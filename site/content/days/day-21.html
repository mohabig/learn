Third ship day. The repo is an agent with real tools, a harness that scores it, and a gate that blocks a bad change — a rarer combination than it should be. Publish it so a stranger can see all three in two minutes.

The section that does the work is "How I evaluate this"

Most repos show what a system does. Yours shows how you know it works, and that is the part a reader cannot fake having read.

So give it its own heading, and put six things under it. How the dataset was built and how many cases it holds. What the assertions check. What the judge asks, and how often it agreed with your own labels. The gate threshold, and why it sits there. The current scores, including the per-cluster breakdown. And the failure clusters you have not fixed yet.

That last one feels wrong to write. Write it anyway. Naming what is still broken reads as confidence, not weakness.

For example: "My search found 3 of the 5 passages I expected. Adding headings helped it find 4. It still misses questions with made-up names." Your own small measurements are useful even when they are not perfect.

So: the eval section is the README, and the rest is scaffolding around it.

Publish numbers, not adjectives

Five numbers, each with its conditions attached: the eval score with the case count and the date, cost per completed task, p95 latency, the median and worst-case step count for the agent, and what red-teaming found.

A number without its denominator is decoration. "0.86 on 40 cases, judge agreement 0.88" beats "high accuracy" by a wide margin, and the reason is simple: the first one can be checked and the second one cannot.

So: write the number, the denominator, and the date, and let the reader do the judging.

The build, step by step

  1. Split the repo cleanly: src/ for the agent and tools, evals/ for the dataset, scorers, and baseline, .github/workflows/ for the gate.
  2. Check that the repo runs from a fresh clone: install, environment variables documented in .env.example, and one command that produces output.
  3. Run the full eval one last time and paste the results table into the README, with the date and the model name.
  4. Write the README top to bottom: what it does in one paragraph for a non-expert, an architecture diagram, "How I evaluate this", the numbers, known failure modes, and what you would do with another week.
  5. Add the CI badge, and link to the commit where a deliberately worsened prompt blocked the merge. That link is the proof.
  6. Confirm no secrets are committed, then scrub the eval dataset of anything private.
  7. Deploy the agent behind an interface a stranger can use, with the spend cap and rate limit from yesterday switched on.
  8. Write five bullets in LOG.md: what surprised you this week, and which of the four ceilings on your loop fired most often.

Where people get stuck

  • Polishing the agent instead of the README. The eval section is the differentiator; the agent is the thing it measures.
  • A public repository or live deployment is optional. Ask a trusted adult to review privacy, costs, and safety before sharing anything.
  • Skipping the fresh-clone test, so the first visitor hits an import error you cannot reproduce.
