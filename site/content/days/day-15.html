Today your model stops being a text box. By tonight it can look something up, do arithmetic, query your database, and write a file. The mechanism underneath is much smaller than the hype: the model asks, and your code decides whether to say yes.

A tool is a description, not a function

Start with what actually leaves your machine. When you give a model a tool, you are not giving it code. You are adding a small block of text to your request — nothing more than that.

That block has three parts. A name, such as sql_query. A description in plain English of what it does and when to use it. And a JSON Schema listing the arguments and their types. That is everything the model ever sees. It has no reach into your function, your database, or your machine.

Think of a menu. The model can read the menu and point at a dish. It never walks into the kitchen, and it never learns what the kitchen looks like. Your code is the kitchen.

So the description is a prompt. In fact it is the whole prompt for this one decision — should I call this, and with what arguments? Watch the difference it makes. "Runs a read-only SQL query against the orders database. Use it for counts, sums, or specific order records. Tables: orders, customers, refunds." gets called correctly. "Queries the DB." gets called at random.

Argument descriptions carry exactly the same weight, so write them the same way: limit — "max rows to return, 1 to 100, default 20".

Now the part that costs money. Tool definitions travel with every single request, so you pay input tokens for them on every call. Four careful tools might cost 400 tokens. Forty tools is a prompt of its own, and the model gets worse at choosing as the list grows. Start with four.

So: a tool is a paragraph of text you resend on every call, and how carefully you write it decides whether it ever gets used.

The round trip: who actually runs the code

Here is the entire mechanism. Learn it once and you have learned every agent framework you will ever adopt, because all of them are wrappers around these four steps.

One: you send the conversation plus the tool definitions.

Two: the model replies with a stop reason meaning "I want a tool", and a block holding the tool name, the arguments as JSON, and an identifier for this specific call. Nothing has run yet. Read that again, because it is the whole idea — the model emitted a description of a call it would like made. It is a request, not an action.

Three: your code parses those arguments, checks them, runs the real Python function, and gets a result. This is the step where you are in charge, and it is the only step where anything actually happens.

Four: you append two things to the message list — the model's request exactly as it came back, and a tool-result message carrying the output plus that same call identifier. Then you send the whole conversation again.

Why the whole conversation? Because the API is stateless. It remembers nothing between requests. Your growing message list is the memory of the interaction; there is no session on the other end holding your place. From there the model either answers in plain text or asks for another tool, and around you go.

The common break is small and maddening: you append the result but forget to append the model's request first. The pair no longer matches, and you get either an API error or a model that asks for the same thing again.

So: the model requests, your code runs it, and both halves of that exchange go back into the list before you send it again.

Choosing tools, and calling several at once

You control how eager the model is, with one setting per request. Auto lets it decide, and is the default. None forbids tools for that turn. Required forces it to pick something. Naming one exact tool forces that call.

That last one deserves a second look, because it is the trick behind reliable structured output from Day 3. Define a tool whose schema is your output shape, then require it. Now the model has to fill in your fields.

Here is the other thing one reply can do: ask for several tools at once. That happens when the calls do not depend on each other — search the web and check the calculator, where neither needs the other's answer first.

Run those concurrently, then return all the results in one message. Split them across separate messages and the pairing breaks; the model quietly stops batching, and every later turn costs you an extra round trip.

So: decide how much freedom the model gets, and when it asks for three things at once, answer all three in one breath.

Errors are results, not crashes

Your SQL tool will receive a malformed query. Not maybe — it will.

The instinct is to let the exception propagate. That kills the loop, and the person waiting gets nothing at all.

Do this instead. Catch it, and send the error text back as the tool result, flagged as an error: relation "order" does not exist; tables are orders, customers, refunds. Models are good at fixing a query when you show them the message. That one behavior converts a large share of your failures into self-repair.

Two limits keep self-repair from becoming a treadmill. Cap retries of the same tool at two, then stop and report honestly.

And truncate results. A fetched web page can be 200,000 tokens, and once it is in the conversation you pay for it on every remaining step. Return the first 2,000 tokens plus a note that it was cut.

So: an error is just one more thing the model can read, but an untrimmed result is a bill you keep paying.

The build, step by step

  1. Define four tools by hand — web_search, calculator, sql_query, file_write — each with a name, a two-sentence description, and a JSON Schema with described arguments. No framework.
  2. Write a dispatch table: a dict from tool name to the Python callable that implements it.
  3. Validate arguments with a Pydantic model before executing. The model produced that JSON from text, so treat it as untrusted input.
  4. Make sql_query safe by construction: a read-only connection, a forced row limit, and a reject on anything that is not a single SELECT.
  5. Make file_write take a bare filename, join it to one output directory, and reject any name containing a path separator or a parent reference.
  6. Write the loop: send messages and tools, check the stop reason, run the requested tools, append the request and the results, send again.
  7. Log every call — tool name, arguments, duration, result size in tokens, running cost. You need this on Day 18, and it is much easier to add now.
  8. Test with a question that needs two tools ("how many orders shipped last month, and what is that per day?") and one that needs none.

Where people get stuck

  • A vague description, then blaming the model for not calling the tool. Rewrite the description before you touch anything else.
  • Trusting the arguments. Never concatenate them into SQL, a shell command, or a file path.
  • Enormous tool results. One un-truncated page can triple the cost of every later step of the conversation.
  • One mega-tool with a mode argument. The schema is what the model reasons over, so split it into real tools.
