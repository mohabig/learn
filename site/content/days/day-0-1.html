This optional setup page is for learners exploring a terminal with a trusted adult. The main course can begin at Day 1 and does not require shell commands. Never type a command you do not understand; ask first.

Keep this safe and simple

Only explore a practice folder. Do not install, delete, download, change system settings, use administrator commands, or copy commands from the internet without an adult checking them. The technical walkthrough below is an optional adult-supported extension.

A terminal is a conversation with your computer

The terminal lets you type a short instruction and see what your computer does. It can help you find a folder or run a program. You can learn the basics without changing or deleting anything.

Think of it like a tiny robot: it waits for an instruction, follows it literally, and shows what happened. It does not know what you meant if you make a typo.

Start with a harmless instruction that lists files or shows which folder you are in. Ask an adult before trying anything that installs, deletes, downloads, or changes files.

The shell does hold one piece of state you have to keep in your head: the working directory. That is where you are standing. pwd prints it, cd changes it, ls lists what is there.

Every relative path you type is resolved against that spot. A path starting with / is absolute — a route from the root of the disk, meaning the same thing no matter where you stand. Anything else starts from where you are, where . means here, .. means the directory above, and ~ means your home directory.

Now, back to the split. Because the shell splits on spaces, a file called my notes.txt arrives at the program as two arguments — and the program, told to open something called my, reasonably reports it can't find it. Quote it. The split happens before the program ever sees your line, so no program can fix this for you.

So: the shell cuts your line into words and runs the first one, starting from wherever you're standing.

Flags, and the three streams

Flags look like a little language with grammar. They aren't. A program receives one plain list of strings, and flags are just strings with a convention attached: one dash for a single letter (-l), two for a whole word (--recursive), and some expect a value in the next string along.

There is no universal rule, which is why every program has to tell you its own. That is what --help is for, on nearly every program you will ever run, and man ls opens the full manual for the version installed on your machine. Read those before a search engine — the forum answer is usually about a different version.

Now the part that pays for itself all week. Every running program gets three streams. Standard input is where it reads from. Standard output is where its results go. Standard error is where its complaints go.

Two output holes, not one, and that is deliberate. It means you can keep the results and throw away the noise, or read the noise and ignore the results, without either one contaminating the other.

The redirections follow from that. > sends standard output to a file, replacing what was there. >> appends instead. 2> sends standard error to a file — the 2 is just that stream's number.

And then the pipe. | connects one program's standard output directly to the next one's standard input, so data flows through a chain without ever touching the disk. Errors stay out of the pipe, which is why a broken stage prints to your screen instead of poisoning the data downstream.

So: results and complaints leave through different doors, and the pipe is a hose from one program's results to the next one's input.

PATH, and why "command not found" happens

Every process carries a dictionary of strings around with it, called its environment, inherited from whatever started it. env prints yours. Look at it once — there is nothing mystical in there, just names and values.

You can set one for a single command by putting it in front (DEBUG=1 python app.py), or for the rest of the session with export. Here is the rule that catches people: environments pass from parent to child and never sideways. Set a variable in one terminal and a second window knows nothing about it, because that window is not the first one's child.

One of those strings is PATH: a list of directories separated by colons. When you type uv, the shell walks that list from left to right, runs the first file named uv it finds, and stops looking. It does not search your disk. which uv tells you which one won.

So why does this matter? Because "command not found" almost never means the install failed. It means the program landed in a directory that is not on your PATH — which the installer told you, in the line you scrolled past.

This is not trivia you get to forget after today. Tomorrow, activating a Python environment turns out to be exactly this and nothing more, and on Day 1 of Week 1 your API key is an environment variable read out of this same dictionary.

So: a program is findable only if its directory is on the list, and the leftmost match wins.

Read the error from the top

A failed install prints hundreds of lines, and the last one is almost always useless: "command failed with exit code 1". That is the symptom — the last program in a chain announcing that something upstream went wrong.

The cause is higher up. Scroll back to the first line containing error, fatal, No such file, or Permission denied, and read that line literally, word by word. It names a file, a version, or a missing piece, and that name is usually the whole answer. Everything after it is wreckage.

Programs also report how they did as a plain number. Zero means it worked; anything else means it didn't. echo $? prints the number from the last command, which is how you check a result that printed nothing at all.

Here is the shortcut worth keeping. Nearly every install failure you meet is one of three kinds: the thing isn't on PATH, you're writing to a directory you don't own, or something needs a version you don't have. Before you type a single fix, name which of the three it is.

So: the last line tells you it broke, the first error line tells you why, and there are only three usual whys.

The build, step by step

  1. Open a terminal. Run pwd, then cd ~, then mkdir -p drill/src drill/data. Put three or four text files inside with a few TODO lines scattered through them.
  2. Find files by shape: find drill -name "*.py", then find drill -type f -size +1k. Note that find takes a starting directory, then filters.
  3. Search contents: grep -rn TODO drill. Read the output format — file, colon, line number, colon, the matching line.
  4. Build the pipeline one stage at a time, running it after each addition so you see what each stage did: grep -rho "TODO.*" drill, then | sort, then | uniq -c, then | sort -rn | head -5.
  5. Redirect both streams to different files: ... > report.txt 2> problems.txt. Open both. Confirm the errors never reached report.txt.
  6. Break something on purpose. Install a command-line tool, then in that same window run export PATH=/usr/bin:/bin and call it again. Read the failure, run which, and fix PATH yourself. Then try installing a package into the system Python and read the permission error without reaching for sudo.
  7. Run --help on two commands you used today and man on one. Find a flag you didn't know existed.
  8. Write the five commands you had to look up into a notes file — the start of your LOG.md.

Where people get stuck

  • Reading only the last line of a long failure — the symptom — and never scrolling up to the first error line, which is the cause.
  • Reaching for sudo at the first permission error. It writes files as the administrator, so the next command fails in a stranger way because those files aren't yours.
  • Setting an environment variable in one window and expecting another window to see it. Environments are inherited by children only.
  • Pasting commands from the internet without reading them. A path you don't recognize deserves thirty seconds and a --help.
