Optional peek: text pieces called tokens

A language model does not always handle text one letter at a time. It uses pieces called tokens; a word may be one piece or several. This optional idea helps explain why counting letters can be tricky for a model.

Where do the chunks come from? A tokenizer splits your text using a fixed vocabulary that was built when the model was trained. Think of it as a phrasebook with a set number of entries. Common words earned an entry of their own, so they cost one token. Rare words, names, code, and anything that isn't English weren't worth an entry each, so they get spelled out of smaller pieces.

For ordinary English there's a rough rule: about four characters per token, or about 0.75 words per token. "Rough" is doing real work in that sentence — don't build a budget on it.

Tokens are one way computers divide text into pieces. For this first lesson, the important thing is simply that a model can miss small details—and that you can check its answer.

Now the trap, and it catches everybody once. Tokenizers differ between model families, so a count from a generic library can be off by 10 to 30 percent for the model you're actually calling. Off by 30 percent is the difference between a budget and a wish.

You never have to estimate. Every provider hands you the real number twice: a counting endpoint you can call before the request, and exact usage in the response after it. See the token counting docs.

So: a model uses numbered pieces of text, and its confident answer still needs checking.

The parts of a call

A request is a list of messages. Each message carries a role — user or assistant — and alongside them sits a separate system prompt holding your standing instructions.

Here's the part that surprises people. The API is stateless. The model remembers nothing between calls. A conversation is you resending the entire history every single turn, which is exactly why the tenth turn costs more than the first.

Then the knobs. Temperature acts on the sampling step. At every position the model produces a probability for every token in its vocabulary, and temperature reshapes that distribution before one token is drawn.

Near 0, the highest-probability token wins almost every time. That's nearly repeatable — never guaranteed. Turn it up and the distribution flattens, letting unlikely tokens through.

max_tokens is a hard ceiling on output. Hit it and generation stops mid-sentence, with no apology. Stop sequences end generation the moment they appear, and they aren't included in what you get back.

One portability note, and it's your first: some newer reasoning models reject temperature entirely and give you an effort setting instead.

The response also tells you how it ended, and you should read that field on every call. end_turn means the model finished. max_tokens means you cut it off.

So: a call is a history you resend, a few knobs that reshape sampling, and one field that says whether the answer is finished.

Cost, to the cent

Every response comes back carrying usage numbers: input tokens, output tokens, cached tokens. The arithmetic is one line — put the two prices in your code as constants, multiply, and print the result next to the answer.

Do it per call, not per month. A monthly number arrives far too late to change anything you did.

Watch what the per-call number does for you. Three thousand input tokens and seven hundred output, at $3 and $15 per million, is $0.0195 — about two cents. Twenty debugging runs is 39 cents. Ten thousand users a day is $195.

That's one number answering two different questions: can you afford to iterate this afternoon, and can this product exist at all.

Two traps. The first is guessing from character counts, which you now know better than to do. The second is quieter: failures bill too. A call that produced 400 tokens before your client gave up still generated 400 tokens, and you pay for all 400.

So: print the cost of every call, in cents, right next to its output.

Two clocks

Two numbers, not one. Time to first token is the gap between sending the request and the first piece of the answer showing up. Total time runs until the last token.

They move for different reasons, and that's the useful part. The first clock is queueing plus the model reading your input, so it grows with prompt length. The second is generation — roughly output tokens divided by the model's tokens-per-second rate.

Do that arithmetic once and it sticks: a 900-token answer at 60 tokens per second takes 15 seconds, no matter how fast the model started.

So the split tells you what to fix. Long prompt, short answer: attack the input. Short prompt, long answer: attack the output, or stream it.

And one fact about people. They perceive time to first token as speed. That is the entire reason streaming exists, and you build it on Day 5.

So: measure both clocks separately, because they have different causes and only one of them is yours to fix today.

The build, step by step

  1. Create the repo, run uv init, add your provider's SDK, and put your key in a .env file that .gitignore already covers.
  2. Write one input function: given a URL or a file path, return plain text. Fetch or read, strip markup, and stop at a token count you chose deliberately, so one huge page can't surprise you.
  3. Write one call. The system prompt states the contract — a title, three bullet points, one open question. Set temperature to 0, max_tokens to 500.
  4. Print the usage numbers from the response and compute cost inline from your price constants. Print the stop reason too; it's how you learn whether the answer is whole.
  5. Wrap the call in a monotonic timer. Stream it so you can record the clock time of the first chunk and the last. Print both.
  6. Run it on five inputs of very different sizes. Put the rows in LOG.md: tokens in, tokens out, cost, first-token time, total.
  7. Set temperature to 1.0 and run the same input three times. Write down what changed and what didn't — that's the knob explaining itself.
  8. Commit. Day 1 ends with a commit even if the day went badly.

Where people get stuck

  • Counting tokens with a library built for a different model family, then wondering why the bill doesn't match the estimate.
  • Setting max_tokens too low and shipping silently truncated output. If you never read the stop reason, you never find out.
  • Timing the whole program instead of the request. Imports and file reads pollute the number, so start the clock immediately before the call.
  • A key pasted into a notebook cell, then committed. Once it's in git history, rotating the key is the only real fix.
